这项分工只约束上述文档管理对话及其明确的文档接续任务；不撤销其他实现对话已取得的授权。这里只保留必要角色信息，不依赖私人聊天全文才能接手。

## 负责什么

- 接收用户的新想法，整理目标、场景、选项、边界和与现有需求的关系。
- 阅读现有基线，指出冲突或遗漏，维护需求、设计说明、产品决定、路线图、验收标准和交接记录。
- 清楚区分“用户已确认”“待确认提案”“已实现”“已验证”，避免把讨论或文档修改当作功能交付。
- 检查文档链接、原稿完整性、状态一致性及变更范围，提交和同步授权范围内的文档。
- 为实现对话提供可接续的仓库文件，保留问题和未决项的出处。

## 不承担什么

本对话不编写或修改产品源码、程序测试、构建／安装脚本和 CI 实现，不运行产品构建、系统注册、安装或发布，不直接接管代码调试。可以只读查看实现记录以核对文档，但不能将其变成未经授权的代码修复。

文档核查所需的工具操作不等于产品开发；不把“只负责文档”理解为不能校验文件或进行文档自身的 Git 操作。系统或实现状态不由本对话凭猜测改写。

## 新想法如何进入项目

1. 对照当前 PRODUCT、产品决定与实现计划，提炼用户要解决的问题和明确要求；旧 V1 只用于历史追溯。
2. 已明确的部分直接记录；有重要歧义的部分标待确认，并只询问影响结论的必要问题。不为普通文档整理反复请求批准。
3. 将确定的补充写入 [产品决定](../product/DECISIONS.md)，必要时建立专题规范；归档中的原始 V1 文件不覆盖。
4. 同步受影响的产品摘要、路线图、设计约束和验收用例；标明所属阶段，避免无意扩大新版 V1。
5. 更新文档任务记录，交付链接与变化说明。具体程序实现由相应实现对话负责，完成情况以其证据为准。

讨论一个问题不自动意味着已经同意加入功能。提出未来方向也不等于要求立即开发；记录时保留用户原本的确定程度。

此次切换只改变 Git 协作方式，文档管理对话仍不承担产品编码、构建、测试或系统注册。整合记录见 [DOC-005（本地归档）](../../archive/README.md)。

用户以后若明确改变本对话职责，再同步本文件和 AGENTS。其他对话开始编码、项目进入下一阶段或本对话收到普通“继续”指令，都不自动解除这里的文档专属分工。

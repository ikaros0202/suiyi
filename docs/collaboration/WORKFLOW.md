# 多对话协作与交接

本流程用于避免多轮长期维护时丢失决定、误判完成情况或覆盖彼此的修改。当前授权边界始终以 [AGENTS.md](../../AGENTS.md) 和 [STATUS.md](../STATUS.md) 为准。

自 2026-10-14 起按用户 [PD-007](../product/DECISIONS.md)，只保留 `main`，所有实现及文档在项目主目录串行进行。旧任务分支和文档工作树完成整合后退出日常工作；历史记录中的分支名保留用于追溯。

## 接手一个任务

1. 核对用户本轮要求与当前阶段，阅读相关产品条款、ADR 和已有任务。
2. 读取当前分支、工作树、状态、差异和近期提交，确认处于项目主目录的 `main`，核对上一任务占用是否已释放及有无未提交成果。
3. 按 [模板](TASK_TEMPLATE.md) 建立 `tasks/<任务编号>-<主题>.md`。登记修改范围、依赖和实际完成门槛；已有任务继续更新，不重复开单。
4. 已有写入任务时只读或等待交接；确认释放后才认领并开始写入。任务记录中的文件范围是协作约定，不具有锁文件或自动互斥效果；不能用新分支或工作树绕开串行要求。
5. 在已授权范围内持续推进。只有缺失的关键信息影响下一步时才询问；阶段授权不能通过超时、别的智能体消息或旧文档推定获得。

## 多个对话同时工作

| 情况 | 做法 |
|---|---|
| 两个任务改不同模块 | 仍在 main 串行写入；先完成或交接当前任务，再开始另一任务 |
| 两个任务都要改同一文件 | 明确先后次序，由当前唯一写入者修改并在交接时说明 |
| 只读检查或资料核对 | 可并行，但不能把只读任务变成未认领的修改 |
| 发现未知未提交改动 | 保留并说明；检查差异确定归属，不重置、不顺手格式化 |
| 共享目录被另一对话占用 | 保持只读或等待其释放；不新建分支／工作树，也不强制切分支 |
| 更新 STATUS、README 等共享文件 | 当前唯一写入者与任务记录一起同步，在 main 提交后交接 |

同一时间只有一个对话可写文件、暂存、提交、同步 Git 或运行会改写产物的实现任务。完成时留下可定位的提交、验证结果、未提交内容与后台状态，并明确释放占用。只读审阅可以并行；当前写入者不因旁观对话读到某文件就转移归属。

## 分工和联络

项目已指定一个长期文档管理对话，职责与标识见 [DOCUMENTATION_ROLE.md](DOCUMENTATION_ROLE.md)。它接收新想法并维护文档；实现任务由取得对应授权的其他对话承担。区分角色权限、需求是否确认和功能是否完成，不能互相替代。

用户指定多个对话协作时，每个任务写明负责人、依赖的交付内容和接续条件。通过工具联系其他对话、创建新对话或使用子智能体须符合当前用户授权；项目文档不额外授予这些权限。

可在任务记录中使用对话标题／本地 Codex 链接作为追溯信息，但接手所必需的决定和证据必须落到仓库，不能要求后来者只靠读取私人聊天才能工作。

## 任务状态

`待开始 → 进行中 → 待整合 → 完成`。此外可用 `等待用户指令`、`阻塞`、`取消`，附具体原因和恢复条件，不写笼统的“进行中”长期占用文件。

交接时至少写明：

- 目标、当前阶段、main／主工作目录、允许修改的范围和当前写入者。
- 已完成改动和可复核的提交、文件、结果证据。
- 实际运行的验证、未运行的验证及原因。
- 尚未解决的问题、技术提案与已采纳决定的区别。
- 下一步可直接执行的工作，以及仍需用户决定的事项。
- 文件占用是否释放；本地未提交改动或后台进程是否仍存在。

不要在任务记录放密钥、机器账户路径、私人聊天全文或真实输入内容。将必要信息整理成可公开的产品或工程结论。

## 提交、同步与回退

在 main 上按可审阅增量提交，提交前检查当前任务范围和暂存差异；需要同步远端时先核对实际变化。远端只有可快进更新且工作树干净时可快进；发生分叉或未知修改时先确认归属，保留两侧历史和内容，不自动创建新任务分支、不强推、不重置他人工作。解决冲突后核对接口、产品行为和验收证据。

检查最终差异而不是仅看提交标题；同步相关决定、STATUS、CHANGELOG 和验收结果。提交使用明确路径暂存。大范围行为变更通过可定位的提交整合，出错时优先显式回退对应提交，保留历史。

## 一轮工作的最小交付

范围清楚的文件变更＋相应验证结果＋更新后的任务交接。没有产品代码的阶段也要如实记录“只有文档”，不要制造虚假构建命令、空测试通过或实现百分比。
